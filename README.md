# Сервис записи на творческие занятия

Учебный сквозной проект по дисциплине «Технологии разработки приложений на базе фреймворков». ПР5: начальный веб-интерфейс Django поверх объектной модели и JSON-хранилища ПР3. ПР6: страницы переведены на шаблоны Django и статические файлы. ПР7: данные перенесены в базу SQLite, списки и статистика строятся SQL-запросами. Консольная версия сохранена.

## Веб-версия

Три Django-приложения отвечают за главную страницу (`homepage`), занятия (`workshops`) и записи (`bookings`). Представления собирают контекст и вызывают `render()`, HTML формируют шаблоны Django. Функция `page()` из ПР5 удалена: HTML-строк в Python-коде представлений больше нет.

Источник данных зависит от страницы: списки, поиск и статистика (ПР7) получают данные SQL-запросами из `data/studio.sqlite`, карточки занятия и записи по-прежнему загружают объекты `Workshop` и `Booking` из JSON.

| URL | Представление | Страница | Данные |
| --- | --- | --- | --- |
| `/` | `homepage.views.index` | Главная, назначение сервиса | нет |
| `/workshops/` | `workshops.views.workshop_list` | Каталог занятий, `?master=<id>` оставляет занятия одного мастера | SQLite |
| `/workshops/available/` | `workshops.views.available_workshops` | Поиск свободных занятий на дату для возраста | SQLite |
| `/workshops/masters/` | `workshops.views.master_list` | Мастера, число занятий и средняя цена | SQLite |
| `/workshops/<int:workshop_id>/` | `workshops.views.workshop_detail` | Занятие, мастер, условия и свободные места | JSON |
| `/bookings/` | `bookings.views.booking_list` | Активные и отменённые записи | SQLite |
| `/bookings/statistics/` | `bookings.views.statistics` | Статистика каталога, записей и участников | SQLite |
| `/bookings/<int:booking_id>/` | `bookings.views.booking_detail` | Участник и ссылка на занятие | JSON |

Маршруты имеют имена и пространства имён (`app_name`): `homepage:index`, `workshops:list`, `workshops:available`, `workshops:masters`, `workshops:detail`, `bookings:list`, `bookings:statistics`, `bookings:detail`. Навигация: Главная, Занятия, Мастера, Записи, Статистика; поиск свободных занятий открывается кнопкой со страницы каталога. В шаблонах ссылки строятся тегом `{% url %}`, жёстко заданных адресов нет. Корневой `creative_studio/urls.py` передаёт обработку приложению через `include()`. Числовой конвертер передаёт ID в представление как `int`.

Два случая HTTP 404:

- Неизвестный адрес, например `/unknown/` или `/workshops/abc/`: при `DEBUG=False` вызывается `handler404` → `homepage.views.page_not_found`. При `DEBUG=True` Django показывает техническую страницу.
- Отсутствующая сущность, например `/workshops/999/` или `/bookings/999/`: маршрут найден, функция поиска возвращает `None`, в шаблон передаётся `None`, и ветка `{% else %}` выводит сообщение. Представление вызывает `render(..., status=404)`. Глобальный обработчик при этом не вызывается.

### Шаблоны (ПР6)

```text
templates/                      общие шаблоны проекта (TEMPLATES["DIRS"])
├── base.html                   каркас: head, Bootstrap, свой CSS, шапка, подвал, JS
└── includes/navigation.html    навигация
homepage/templates/homepage/
├── index.html                  главная
└── page_not_found.html         глобальная страница 404
workshops/templates/workshops/
├── workshop_list.html          каталог
├── workshop_detail.html        карточка занятия
└── includes/workshop_card.html одно занятие в каталоге
bookings/templates/bookings/
├── booking_list.html           список записей
├── booking_detail.html         одна запись
└── includes/booking_status.html статус записи
```

Используемые возможности Django Template Language:

- наследование: каждая страница начинается с `{% extends "base.html" %}` и переопределяет блоки `{% block title %}` и `{% block content %}`;
- включаемые шаблоны: навигация, карточка занятия и статус записи подключаются через `{% include %}`; статус используется и в списке, и на странице записи;
- контекст: например `{"workshops": [(занятие, свободные места), ...]}` для каталога, `{"booking": booking}` для записи;
- циклы `{% for %}` с `{% empty %}` для пустых списков («Занятий нет.», «Записей нет.»);
- условия `{% if %}`: найден ли объект, есть ли места, активна или отменена запись;
- фильтры: `length` (число занятий и записей), `default` (название занятия), `date:"d.m.Y"` (даты), `floatformat:"2u"` (цена с двумя знаками).

Логика предметной области осталась в Python: свободные места и доступность записи считаются в представлении методами `Workshop`, шаблон только выводит результат. Автоэкранирование Django заменило ручной `escape()` из ПР5.

### Запуск веб-версии

Нужен Python 3.10+; установленная версия Django ограничена веткой 5.2. Из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py runserver
```

Открыть <http://127.0.0.1:8000/>. Остановка сервера — `Ctrl+C`. Если используется существующее окружение ПР2, замените `.\.venv\Scripts\python.exe` на `.\мусор\.venv_pr2\Scripts\python.exe`.

`migrate` подготавливает служебную базу `db.sqlite3` для встроенных приложений Django (авторизация, сессии и админка). Это не база проекта: занятия и записи туда **не переносятся**, их база `data/studio.sqlite` создаётся отдельно скриптом ПР7 (см. раздел «База данных SQLite»). Файл `db.sqlite3` исключён из Git; после клонирования миграции нужно выполнить снова. `/admin/` — стандартная служебная страница, не часть пользовательского интерфейса ПР5.

Для демонстрации собственной страницы 404 перезапустите сервер так:

```powershell
$env:DJANGO_DEBUG = "0"
.\.venv\Scripts\python.exe manage.py runserver --insecure
```

При `DEBUG=False` сервер разработки сам не отдаёт статические файлы, поэтому нужен флаг `--insecure`; без него страницы откроются без CSS, логотипа и JavaScript. `ALLOWED_HOSTS` уже содержит `localhost`, `127.0.0.1` и `[::1]`. Вернуть режим отладки можно значением `$env:DJANGO_DEBUG = "1"` и перезапуском сервера. По умолчанию отладка включена. Конфигурация предназначена только для локальной учебной работы; при публикации необходимы отдельный секрет `DJANGO_SECRET_KEY` и безопасные настройки развёртывания.

Веб-версия поддерживает чтение (`GET` и `HEAD`), не изменяет данные и отклоняет `POST` кодом 405. Создание и отмена записей остаются в консоли. Django ORM, собственные модели Django и формы ещё не используются: база подключена напрямую через `sqlite3`. Отдельного приложения пользователей пока нет; класс `User` описывает участника занятия, а `django.contrib.auth` — встроенную систему учётных записей Django.

Для загрузки Bootstrap нужен интернет; собственные стили, логотип, скрипт и данные доступны без CDN.

## База данных SQLite (ПР7)

На ПР7 данные сервиса перенесены из JSON в базу SQLite `data/studio.sqlite`. База работает напрямую через стандартный модуль `sqlite3`, без Django ORM. Путь данных для страниц списков:

```text
data/*.json -> db/import_json.py -> data/studio.sqlite -> SQL -> представление -> context -> шаблон
```

### Структура базы

В JSON мастер хранится строкой внутри занятия, а участник (имя и возраст) внутри записи. В базе это отдельные таблицы, связанные внешними ключами.

| Таблица | Поле | Тип | Назначение |
| --- | --- | --- | --- |
| `masters` | `id` | INTEGER | первичный ключ |
| | `name` | TEXT NOT NULL UNIQUE | имя мастера |
| `workshops` | `id` | INTEGER | первичный ключ |
| | `name` | TEXT NOT NULL | название занятия |
| | `master_id` | INTEGER NOT NULL | внешний ключ на `masters.id` |
| | `date` | TEXT NOT NULL | дата `ГГГГ-ММ-ДД`, такие строки правильно сравниваются и сортируются |
| | `price` | REAL NOT NULL | стоимость, руб. |
| | `capacity` | INTEGER NOT NULL | вместимость |
| | `minimum_age` | INTEGER NOT NULL DEFAULT 0 | минимальный возраст |
| | `description` | TEXT | описание, может быть NULL: в JSON описаний пока нет |
| `users` | `id` | INTEGER | первичный ключ |
| | `name` | TEXT NOT NULL | имя участника |
| | `age` | INTEGER NOT NULL | возраст, пара `(name, age)` уникальна |
| `bookings` | `id` | INTEGER | первичный ключ |
| | `workshop_id` | INTEGER NOT NULL | внешний ключ на `workshops.id` |
| | `user_id` | INTEGER NOT NULL | внешний ключ на `users.id` |
| | `status` | TEXT NOT NULL DEFAULT 'active' | `active` или `cancelled`, ограничено `CHECK` |

Связи: у мастера может быть несколько занятий, у занятия и у участника может быть несколько записей. Каждая запись относится к одному занятию и одному участнику.

### Файлы

| Файл | Назначение |
| --- | --- |
| `sql/schema.sql` | `CREATE TABLE IF NOT EXISTS` для четырёх таблиц, повторный запуск не вызывает ошибку |
| `sql/queries.sql` | 13 проверенных запросов с комментариями |
| `db/database.py` | `get_connection()` с `PRAGMA foreign_keys = ON`; `fetch_all()` и `fetch_one()` для представлений с `row_factory = sqlite3.Row` |
| `db/import_json.py` | Перенос JSON в базу: создать схему, очистить таблицы, вставить данные через `executemany()` |
| `data/studio.sqlite` | Файл базы данных |

### Создание базы и перенос данных

Из корня проекта:

```powershell
.\мусор\.venv_pr2\Scripts\python.exe -m db.import_json
```

Скрипт сам выполняет `sql/schema.sql`, затем очищает таблицы и заново переносит оба JSON-файла, поэтому его можно запускать повторно. Вставка идёт в порядке `masters`, `workshops`, `users`, `bookings`: сначала строки, на которые ссылаются внешние ключи. `master_id` и `user_id` находятся подзапросами по имени мастера и по имени и возрасту участника. Весь перенос выполняется одной транзакцией: при ошибке `rollback()` оставляет базу в прежнем состоянии.

Консоль по-прежнему сохраняет изменения в JSON. После записи или отмены через `main.py` нужно снова запустить импорт, иначе списки на сайте покажут старые данные.

Проверка в интерактивном Python:

```python
import sqlite3
conn = sqlite3.connect("data/studio.sqlite")
conn.execute("SELECT name FROM sqlite_master WHERE type='table'").fetchall()
conn.execute("PRAGMA foreign_key_list(bookings)").fetchall()
conn.execute("SELECT COUNT(*) FROM workshops").fetchone()
```

Ожидается 4 таблицы, 2 внешних ключа у `bookings`, 3 занятия и 2 записи для данных репозитория. Запросы из `sql/queries.sql` можно выполнить в SQLite CLI (`sqlite3 data/studio.sqlite`) или в SQLite Viewer в VS Code.

### SQL-запросы

| № | Запрос | Конструкции | Где используется |
| --- | --- | --- | --- |
| 1 | Каталог со свободными местами | SELECT, LEFT JOIN, COUNT, GROUP BY, ORDER BY | `/workshops/` |
| 2 | Мастер по ID | WHERE | `/workshops/?master=1` |
| 3 | Занятия одного мастера | LEFT JOIN, WHERE, COUNT, GROUP BY | `/workshops/?master=1` |
| 4 | Свободные занятия на дату для возраста | LEFT JOIN, WHERE, GROUP BY, HAVING | `/workshops/available/` |
| 5 | Мастера с числом занятий и средней ценой | LEFT JOIN, COUNT, AVG, GROUP BY | `/workshops/masters/` |
| 6 | Все записи с занятием и участником | JOIN трёх таблиц | `/bookings/` |
| 7 | Показатели каталога | COUNT, MIN, MAX, AVG | `/bookings/statistics/` |
| 8 | Записи по статусам | COUNT, GROUP BY | `/bookings/statistics/` |
| 9 | Выручка по активным записям | JOIN, WHERE, SUM | `/bookings/statistics/` |
| 10 | Участники и их активные записи | LEFT JOIN, COUNT, GROUP BY | `/bookings/statistics/` |
| 11 | Популярные занятия | JOIN, WHERE, GROUP BY, HAVING | `/bookings/statistics/` |
| 12 | Занятия без описания | WHERE IS NULL | консоль SQLite |
| 13 | Самые дорогие занятия со сдвигом | ORDER BY, LIMIT, OFFSET | консоль SQLite |

WHERE отбирает строки до группировки, HAVING отбирает группы после неё. В запросах 1, 3, 4 и 10 условие `status = 'active'` стоит в `ON`, а не в `WHERE`: так `LEFT JOIN` сохраняет занятия и участников без активных записей, а `COUNT(bookings.id)` даёт для них 0.

### Получение данных в Django

Представления выполняют SQL через `fetch_all()` и `fetch_one()` из `db/database.py`. Эти функции открывают соединение, ставят `conn.row_factory = sqlite3.Row`, выполняют запрос и закрывают соединение. Благодаря `sqlite3.Row` шаблон обращается к полям по имени: `{{ workshop.name }}`, `{{ booking.user_name }}`, а не по индексу.

Значения от пользователя передаются только параметрами `?`:

```python
workshops = fetch_all(AVAILABLE_QUERY, [day.isoformat(), age])
```

Дата и возраст из формы поиска сначала проверяются в `parse_search()`: неверная дата или возраст вне 0–120 выводят сообщение, запрос к базе при этом не выполняется. Подстановка значений в текст SQL через f-строки и конкатенацию не используется.

## Назначение и аудитория

Сервис помогает посетителям творческих студий выбрать занятие, проверить условия участия и записаться к мастеру. Мастер проводит занятие в определённую дату; у занятия есть стоимость, вместимость и минимальный возраст. Запись связывает участника с занятием. Свободные места вычисляются как вместимость минус число активных записей.

## Возможности

1. Просмотр занятий и поиск по части названия без учёта регистра.
2. Фильтрация по возрасту, дате и свободным местам.
3. Сортировка по возрастанию цены или даты.
4. Проверка возраста, даты, мест и отсутствия повторной активной записи.
5. Создание записи после подтверждения, сохранение между запусками.
6. Отмена записи с освобождением места и сохранением истории.
7. Просмотр записей, добавление занятий и статистика.

Это возможности консольной версии. Все пункты меню ПР2 сохранены. Пункт 0 завершает работу, после остальных действий программа возвращается в меню.

## Объектная модель

| Класс | Атрибуты | Поведение |
| --- | --- | --- |
| `User` | `name`, `age` | Проверка участника, `identity()` для поиска повторной записи, `__str__()` |
| `Master` | `name` | Проверка имени ведущего, `__str__()` |
| `Workshop` | `id`, `name`, `master`, `date`, `price`, `capacity`, `minimum_age` | `available_seats()`, `check_booking()`, `to_data()`, `from_data()`, `__str__()` |
| `Booking` | `id`, `workshop`, `user`, `_status` | `cancel()`, свойство `status`, `to_data()`, `from_data()`, `__str__()` |

Классы размещены в отдельных модулях пакета `models`. Через `models/__init__.py` доступны импорты `from models import Workshop, Booking, User, Master`. Функции обработки коллекций находятся рядом с соответствующими классами.

Все классы имеют явный `__init__`. Конструкторы проверяют обязательные данные; возможность новой записи дополнительно проверяется с учётом всей коллекции.

`Booking.workshop` ссылается на тот же объект `Workshop`, который находится в каталоге. `Booking.user` содержит объект `User`, а `Workshop.master` — объект `Master`. Это композиция. Внутри программы коллекции содержат объекты; общий контейнер `State` — типизированный словарь двух списков.

Статус записи доступен через `@property` и изменяется методом `cancel()`. Это пример инкапсуляции. Единый вызов `str()` для разных классов демонстрирует полиморфизм. Наследование здесь не требуется: между занятием, записью, участником и мастером нет необходимого отношения «является». `@classmethod` используется для восстановления объектов из данных.

## Что изменилось после ПР2

- Словари сущностей заменены объектами с атрибутами и методами.
- Проверка доступности и расчёт мест относятся к `Workshop`, отмена — к `Booking`.
- Поиск, сортировка, фильтрация и добавление в коллекции остаются функциями.
- Функции `show_workshop`, `check_booking` и `create_booking` сохраняют сценарий ПР1 и работают с объектами.
- Меню отвечает за диалог; файловые операции остаются в `storage.py`.
- Общий `state.json` заменён двумя файлами по сущностям. Существующие ID, занятия и записи перенесены без изменения значений.
- Тесты ПР2 адаптированы; добавлены проверки классов и восстановления связей.

| `data/bookings.json` | Записи с данными участников и ссылкой workshop_id |

## Хранение данных

Оба JSON-файла содержат списки. В `workshops.json` у занятия сохраняются `id`, `name`, `master`, `date`, `price`, `capacity`, `minimum_age`. В `bookings.json` у записи сохраняются `id`, `workshop_id`, `user_name`, `user_age`, `status`.

Данные мастеров и участников остаются внутри соответствующих сущностей, как в ПР2: отдельных справочников и учётных записей пока нет. Поэтому для четырёх классов достаточно двух файлов.

При загрузке сначала создаются занятия, затем записи со ссылками на загруженные занятия. Несуществующие ссылки, повторные ID, повторные активные записи, неверный возраст и превышение вместимости отклоняются. Прошедшие занятия и отменённые записи загружаются для сохранения истории. Даты в JSON имеют формат `ГГГГ-ММ-ДД`, в объектах — `datetime.date`, при вводе — `ДД.ММ.ГГГГ`.

Добавление занятия сохраняет только `workshops.json`. Создание и отмена записи сохраняют только `bookings.json`. Перед сохранением проверяются всё состояние и соответствие второй коллекции её файлу. Изменяемый файл записывается во временный файл в той же папке, затем атомарно заменяется через `os.replace`. Состояние в памяти обновляется после успешного сохранения. Ошибка записи не применяет действие.

Повреждённые данные останавливают запуск и не перезаписываются. Отсутствующий файл считается пустой коллекцией; записи без соответствующего каталога отклоняются. Если оба файла отсутствуют, можно добавить первое занятие через пункт 9. Пути определяются относительно `main.py`.

В каталоге три занятия на 10–12 октября 2026 года. Даты не сдвигаются автоматически. После их наступления новые занятия добавляются через меню.

## Проверка

```powershell
.\мусор\.venv_pr2\Scripts\python.exe -m pytest
.\мусор\.venv_pr2\Scripts\python.exe -m flake8
```

Тесты используют независимые данные и временные файлы. Проверяются все пункты меню, ограничения записи, отмена и повторная запись, поиск, сортировка, фильтрация, конструкторы и строковое представление, связи объектов, перезапуск, два файла JSON и ошибки сохранения. Основные функции и методы имеют аннотации типов.

В `tests/test_web.py` дополнительно проверяются пять страниц, подключение статических файлов из `base.html`, фильтр `length`, отсутствие `page()`, именованные маршруты, числовые ID, оба случая 404, режим отладки, чтение изменённого JSON, экранирование HTML, пустые списки, места и статусы, запрет POST и отсутствие изменений файлов при просмотре. Для страниц ПР7 проверяются поиск свободных занятий (дата, возраст, заполненное занятие, неверный ввод), страница мастеров и фильтр каталога, статистика и пустая база. Django-тесты выполняются обычным pytest без тестовой БД Django: каждый тест создаёт временные JSON и переносит их во временную `studio.sqlite`.

В `tests/test_database.py` проверяются создание таблиц, перенос данных, повторный импорт, внешние ключи, ограничение `CHECK` для статуса и откат импорта при ошибке.

Для отладки поставьте точку останова на `bookings.append(booking)` в `models/bookings.py`, выберите пункт 6 и подтвердите запись. У объекта можно просмотреть `booking.user` и `booking.workshop`.

## Ограничения

Программа рассчитана на локальные учебные данные. Пользовательской авторизации и реальной оплаты нет; веб-страницы записей доступны без входа, поэтому реальные персональные данные здесь использовать нельзя. Участник определяется сочетанием имени без учёта регистра и возраста; полные тёзки одного возраста не различаются. Имя мастера хранится в занятии, профиль участника — в записи. Отменить запись может пользователь консоли. Одновременная запись нескольких процессов не поддерживается; изменять данные следует одним экземпляром консоли.
