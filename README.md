# Сервис записи на творческие занятия

Индивидуальный проект по дисциплине «Технологии разработки приложений на базе фреймворков». ПР9 переводит веб-интерфейс на Django ORM. Посетитель просматривает занятия, условия участия, свободные места, записи и статистику.

## Запуск

Нужны Python 3.10+ и Django 5.2. Из корня проекта в PowerShell выполните команды.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py import_pr7
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py runserver
```

Открыть <http://127.0.0.1:8000/>. Если используется прежнее окружение, замените `.\.venv\Scripts\python.exe` на `.\мусор\.venv_pr2\Scripts\python.exe`. Остановка сервера выполняется через Ctrl+C. После изменения Python-кода сервер с флагом `--noreload` нужно перезапустить вручную.

## База данных и перенос

Все веб-страницы читают данные через ORM из `db.sqlite3`, указанной в `creative_studio/settings.py`. Миграции четырёх приложений создают таблицы предметной области. Файл базы исключён из Git, миграции входят в репозиторий.

Исходная база ПР7 находится в `data/studio.sqlite`. Команда `import_pr7` читает её в режиме только для чтения и переносит мастеров, участников, занятия и записи одной транзакцией. Сохраняются ID, связи, даты и статусы. Успешный импорт сообщает количество строк каждой сущности. Для исходных данных это 3 мастера, 2 участника, 3 занятия и 2 записи.

Повторный запуск проверяет совпадение существующих строк. При конфликте с изменениями в ORM команда сообщает об ошибке и откатывает перенос. Для выбора другого источника используется `python manage.py import_pr7 --source путь/к/studio.sqlite`. До переноса рекомендуется сохранить копию файла. Резервные копии текущего перехода лежат локально в `мусор/ПР9/backup`.

После первоначального переноса изменения сайта выполняются через ORM. JSON и прежняя база ПР7 автоматически с ORM не синхронизируются. Консоль `main.py` продолжает работать со своим JSON-хранилищем ПР3.

## Модели и структура

| Файл | Назначение |
| --- | --- |
| `masters/models.py` | Master с уникальным именем |
| `users/models.py` | User с именем и возрастом 0–120, уникальной парой имени и возраста |
| `workshops/models.py` | Workshop с мастером, датой, ценой Decimal, вместимостью, возрастным ограничением и необязательным описанием |
| `bookings/models.py` | Booking со ссылками на занятие и участника, статусом active/cancelled |
| `*/migrations/` | Управляемая Django история структуры таблиц |
| `bookings/services.py` | Создание записи с проверками и транзакцией |
| `db/import_sqlite_to_orm.py` | Перенос ПР7 в ORM и обнаружение конфликтов |
| `workshops/management/commands/import_pr7.py` | Команда переноса |
| `workshops/views.py`, `bookings/views.py` | ORM-запросы, обработка параметров и контекст |
| `templates/base.html`, `templates/includes/` | Общий каркас, меню и пагинация |
| `homepage/static/homepage/` | CSS, SVG-логотип, JavaScript с годом в подвале |
| `models/`, `storage.py`, `main.py` | Объектная модель и консоль ПР3 |
| `sql/`, `db/database.py`, `db/import_json.py` | Материалы и средства работы с отдельной базой ПР7 |

Связи «один ко многим» имеют обратные имена `Master.workshops`, `Workshop.bookings` и `User.bookings`. `on_delete=PROTECT` защищает мастеров, занятия и участников, на которых есть ссылки. Сначала удаляется зависимая тестовая запись.

База проверяет допустимый статус, диапазоны цены, вместимости и возраста, уникальность активной записи пары «занятие и участник». `Booking.clean()` дополнительно проверяет возраст, места и повторную активную запись участника с учётом регистра имени. При ручном изменении модели вызывайте `full_clean()` перед `save()`, как принято в Django. Создание записи через `bookings.services.create_booking()` также проверяет дату занятия и резервирует изменение в транзакции. Отмена выполняется методом `cancel()`, история сохраняется.

Обычные классы из корневого пакета `models` используются консолью. Участник `users.User` содержит имя и возраст, встроенная система учётных записей Django обслуживает служебную админку.

## Страницы

| URL | Назначение |
| --- | --- |
| `/` | Главная |
| `/workshops/` | Каталог, `q` ищет название, `master` фильтрует мастера, `sort` задаёт date/name/price/-price |
| `/workshops/<int:workshop_id>/` | Карточка занятия и свободные места |
| `/workshops/available/?date=2026-10-10&age=18` | Поиск на точную дату по возрасту и наличию мест |
| `/workshops/masters/` | Мастера, количество занятий и средняя цена |
| `/bookings/` | Записи, фильтры и постраничный вывод |
| `/bookings/<int:booking_id>/` | Запись с участником, занятием и мастером |
| `/bookings/statistics/` | Цены, записи по статусам, сумма цен активных записей, участники и популярные занятия |

Список записей поддерживает `workshop`, `user`, `date`, `status=active/cancelled`, поиск `q` по имени участника или названию занятия, `sort=date/-date/workshop/user` и `page`. По умолчанию видны все статусы. Неизвестный вариант сортировки заменяется сортировкой по дате. Неверные фильтры выводят сообщение и пустой результат. Paginator показывает 10 записей на странице, параметр `BOOKINGS_PAGE_SIZE` позволяет изменить размер. Некорректный номер страницы приводит к первой, выход за границы — к последней странице. Ссылки `{% querystring %}` сохраняют остальные GET-параметры.

Поиск использует `iregex` с экранированием пользовательского текста. На SQLite это обеспечивает поиск подстроки без учёта регистра, в том числе для русских имён. Ввод не интерпретируется как регулярное выражение.

Свободные места вычисляются в ORM как вместимость минус количество активных записей. Занятия без записей и участники без активных записей учитываются в списках и статистике. Поиск по точной дате допускает просмотр истории. Карточка прошедшего занятия показывает «Запись недоступна». Исходные даты 10–12 октября 2026 года автоматически не сдвигаются.

Представления используют `get_object_or_404()`. При `DEBUG=False` обработчик `homepage.views.page_not_found` показывает сообщение о ненайденном объекте в шаблоне карточки, а для неизвестного URL — общую страницу 404. При `DEBUG=True` Django показывает техническую страницу ошибки. Веб-страницы поддерживают GET/HEAD, POST возвращает 405.

## Django Shell и CRUD

Запустите `python manage.py shell`. Пример создаёт отдельные тестовые объекты. После демонстрации последние строки удаляют их в порядке зависимостей.

```python
from datetime import date, timedelta
from masters.models import Master
from users.models import User
from workshops.models import Workshop
from bookings.models import Booking
from bookings.services import create_booking

master = Master.objects.create(name="Тестовый мастер ПР9")
workshop = Workshop.objects.create(name="Тестовое занятие ПР9", master=master,
    date=date.today() + timedelta(days=7), price=1000, capacity=2, minimum_age=12)
user = User.objects.create(name="Тестовый участник ПР9", age=18)
booking = create_booking(workshop.pk, user)
Booking.objects.get(pk=booking.pk)
workshop.bookings.all()
user.age = 19
user.full_clean()
user.save()
user.refresh_from_db()
user.age
booking.cancel()
Workshop.objects.with_seats().get(pk=workshop.pk).seats
booking.delete()
user.delete()
workshop.delete()
master.delete()
```

Для пустого результата `filter()` возвращает пустой QuerySet. `get()` при отсутствии поднимает `DoesNotExist`, при нескольких строках — `MultipleObjectsReturned`. Во view исключение отсутствия обрабатывает `get_object_or_404()`.

## Проверки и просмотр SQL

```powershell
.\мусор\.venv_pr2\Scripts\python.exe manage.py check
.\мусор\.venv_pr2\Scripts\python.exe manage.py showmigrations
.\мусор\.venv_pr2\Scripts\python.exe manage.py makemigrations --check --dry-run
.\мусор\.venv_pr2\Scripts\python.exe -m pytest -v
.\мусор\.venv_pr2\Scripts\python.exe -m flake8
```

`pytest-django` создаёт отдельную тестовую базу. Веб-тесты ПР5–ПР7 адаптированы к ORM. В `tests/test_orm.py` проверяются CRUD, связи, правила записи, повторный и неудачный импорт, защита изменённых данных, поиск по кириллице, неверные параметры, пагинация и сохранение фильтров в ссылках. Проверяется, что карточка записи загружает связанные сущности одним SQL-запросом. Тесты консоли и прежней SQLite остаются частью набора проверок.

При `DEBUG=True` на localhost подключается Django Debug Toolbar. Откройте карточку записи и панель SQL, чтобы увидеть JOIN таблиц участника, занятия и мастера. В списке записей показывается запрос с выбором полей через values/F. В тестах и при выключенной отладке панель отключается. На Windows MIME-тип JavaScript должен позволять браузеру загрузить скрипты панели.

Для пользовательской страницы 404 задайте `$env:DJANGO_DEBUG = "0"` и запустите `manage.py runserver --insecure`. Флаг используется локальным сервером для отдачи статики при выключенной отладке. Для возврата панели задайте `$env:DJANGO_DEBUG = "1"` и перезапустите сервер.

## Предыдущие этапы и ограничения

Консоль запускается командой `python main.py`. Она сохраняет занятия в `data/workshops.json`, записи в `data/bookings.json`, проверяет возраст, дату, места и повторные записи, поддерживает поиск, сортировку, фильтрацию и отмену. `models/` содержит классы ПР3, `storage.py` проверяет целостность и атомарно сохраняет изменяемый JSON. На этапе ПР7 команда `python -m db.import_json` обновляла отдельную `data/studio.sqlite`. Эти материалы сохранены для воспроизведения предыдущих работ.

Приложение предназначено для локальных учебных данных. Страницы записей доступны без пользовательского входа. Сумма цен активных записей в статистике представляет расчётный показатель, реальные платежи не реализованы. Пользователь определяется именем и возрастом. Для новой локальной копии нужны миграции и первоначальный импорт, затем данные изменяются через ORM.

История этапов отмечена префиксами PR3, PR5, PR6, PR7 и PR9. Материалы Яндекс Практикума в доработку индивидуального проекта не входят.
